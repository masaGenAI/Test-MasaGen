# クイズ問題の作成規約

このリポジトリで過去に実際に起きた欠陥から作った規約。
数字はすべてこのリポジトリのデータを実測したもので、推測ではない。

## 0. 最低100問

**1バッチは必ず100問以上**にする。99問で出さない。
100問に満たないなら、テーマを広げるか、出すのを次に回す。

## 1. 作る前に「直す価値があるか」を測る

既存問題の修正では、**手を付ける前に悪用可能性を測る**。
「最長の選択肢を選ぶ」の正答率が偶然（1/選択肢数）と同等以下なら、
書き直しても学習者が得られるものは変わらない。文字が変わるだけになる。

このリポジトリでの実測例：

| バンク | 「最長を選ぶ」正答率 | 偶然 | 判断 |
|---|---|---|---|
| AI-103 難問 | 70% | 25% | 直す価値がある |
| ガバナンス道場 | 69% | 25% | 直す価値がある |
| MCQS | 22% | 25% | **直さない**（偶然以下） |
| クラウド比較バンク | 32% | 25% | **直さない**（実在する製品名の長さの差） |

## 2. 長さの手がかりは「両方向」潰す

### やってはいけないこと A：正解が最長

内容を知らなくても最長を選べば当たる。これが元々の欠陥だった。

### やってはいけないこと B：正解が絶対に最長にならない

Aを潰すために錯乱肢だけを伸ばすと、今度は**「最長を消す」だけで1択減らせる**。
実際この作業でそうなった（26バンクで「正解が最長」が8%未満、偶然は25%）。
方向が逆なだけで同じ欠陥。

**目標は「正解が最長になる割合が 1/選択肢数 の近く」**。
4択なら25%前後。0%も70%も等しく悪い。
長い選択肢は正解にも錯乱肢にも散らすこと。

### 同点は「潰せていない」

正解と同じ長さの錯乱肢を置いても、**正解が先頭側にあれば最長選択は正解を引く**。
この見落としで12問が検査をすり抜けた。さらにビルド側の判定も
「全錯乱肢が厳密に短い」だったため、**同点パターン1,470問を計上できていなかった**。

判定は必ず**実際に選択肢を組み直して「最長を選ぶ（同点は先頭）」を再現**する。
文字数の比較で済ませない。

## 3. 錯乱肢の長さは「具体的だが誤った内容」で稼ぐ

良い：誤った既定値・誤ったスコープ・誤った順序・誤った閾値や保持期間・
その選択肢が否定している運用の具体像。

禁止：

- 「〜と考えられる」「〜とも言える」だけの付け足し
- 同じ意味の言い換えの羅列
- 中身のない「なお、」「また、」節
- **正しい一般論を足して選択肢を半分正解にすること**（最も危険）

最後のものは、錯乱肢を「部分的に正しい」状態にしてしまい、
問題そのものを壊す。長さのために正しさを足さない。

## 4. 例外的に扱うケース

**否定形の設問**（「適切でないものはどれか」「含まれないものはどれか」）では、
錯乱肢が**正しい記述だからこそ誤答**である場合がある。
この場合は正しいまま厚くする。誤りを注入すると設問が壊れる。

**サービス名・コマンド名など短いラベル**しかない選択肢は、
括弧書きでそのラベル自体の説明を足す。
ただし説明が「なぜそれが誤答か」を明かしてしまわないよう注意する。

## 5. 文字種

- **簡体字**は cp932（Shift_JIS）で符号化できない字で判定する。
  ブラックリスト方式は `国` `数` `体` `点` などの新字体を誤検出する。
  過去に7件混入していた（`効果3分类` `最长期間` `业務利用` `世界で统一` ほか）。
- **キリル文字は cp932 を通る**（JIS X 0208 に収録されている）ので、
  符号化判定では検出できない。`U+0400–U+052F` を別に見ること。
  過去に `банк` を書き込んだことがある。
- 中国当局・機関の正式名称（CAC / 网信办、CNNIC / 中国互联网络信息中心、
  工信部赛迪院、算法备案）は**原語のまま引用するのが正しい**。日本語表記にしない。

## 6. 重複

**設問文が同じでも重複とは限らない。**
「このセクションで最も重視される観点はどれか。」のような汎用文は
複数セクションで使い回されていて、中身は別問題。6件を誤って削除しかけた。

重複かどうかは**設問文＋正解＋選択肢一式**で判定する。
実際に見つかった33件の内訳は、完全一致18・正解の言い換え12・
錯乱肢だけ入れ替え3。後ろ2つも学習上は重複なので削除対象にした。

## 7. 正解位置の分布

正解が特定の位置に偏らないようにする。
全体の実測は 27/26/24/23% だが、バンク単位では40%まで偏っているものがある。
1つの位置が 1/選択肢数 の1.5倍を超えたら散らす。

## 8. 既存バンクに追加・削除するときの注意

- **同名の定数が複数モジュールに存在する。** `BANK` は18箇所、`SET1` は11箇所ある。
  `const BANK = [` の最初の一致だけを見ると別のバンクを触ることになる。
  必ず全宣言を走査し、`(名前, 宣言の番号)` で対象を特定する。
- **端末保存データが配列の添字をキーにしている。**
  `gafa_srs_v1`（MCQS の復習スケジュール）、`acad_quiz_score_v1`（ACAD の正誤）など。
  問題を削除・並べ替えすると、利用者の履歴が隣の問題を指す。
  削除するなら添字の再マッピングを1回だけ走らせる移行処理を入れる。
- **表示している問題数を必ず合わせる。**
  `BOOTCAMP_QUEST.mega` の `qn` の合計が画面の「クイズN問」と一致する必要がある。
  手で書き換えず、実際のバンク長から計算し直す。

## 9. 出典と鮮度

価格・モデル名・料金体系に言及する解説には**必ず時点（年月）を書く**。
「再確認のうえ引用すること」を添える。黙って古くなると誤情報になる。

## 提出前の手順

```bash
# 1. 新規バッチを JSON 配列にして検査する（差し込む前）
node .claude/skills/quiz-authoring/check-batch.mjs new-questions.json --bank GOVDOJO_BANK

# 2. 差し込んだら全体を検査する（ビルドに組み込まれている）
cd nova-app && npm run build
```

`check-batch.mjs` が見るもの：100問の下限／最長選択の悪用（同点含む）／
長さの偏りが両方向とも過剰でないか／正解位置の分布／簡体字とキリル文字／
選択肢の重複・空・正解との一致／水増し表現／自己申告タグ／
バッチ内と既存バンクとの問題重複。

エラーがゼロになるまで差し込まない。警告は内容を見て判断する。
