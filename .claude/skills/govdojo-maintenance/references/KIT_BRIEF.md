# 実務キット（③顧客向けAI・④台帳・⑤検証・⑧リスク管理×AI）― 作成の指示

道場の「分類」は論点と問いの一覧で、**実際に手を動かすための型**がない。そこで4つの実務キットを作る。
読み手はAIガバナンス担当・コンサルタント。手順・項目は**判断（ベストプラクティスの整理）**でよいが、
「○○（規格・ガイドライン・法令）が△△を求めている／勧めている」と書く箇所は、**取得した本文で裏づける**（REG_BRIEF.md と同じ src の形と決まり）。
出典なしで規格名を持ち出さない。義務を作らない（「推奨」と「法的義務」を区別する）。

## 1. cust：顧客向けAIサービスのガバナンス（公開前・運用中・事故時）
- 公開前チェック 10〜14項目：AIであることの表示、利用規約・免責の限界、誤回答の責任の考え方、人への切り替え・苦情窓口、入力してはいけない情報の案内、年齢・脆弱な利用者、アクセシビリティ、ログと保存期間、停止手順、表示・広告の規制（景品表示法など）、評価の合格基準 など。
- 運用中 5〜7項目、事故時 4〜6項目。
- 根拠に使える出典の例：AI事業者ガイドライン（AI提供者・利用者の事項）、EU AI法 第50条（透明性義務）、消費者庁（景品表示法）、個人情報保護委員会の生成AI注意喚起。

## 2. inv：AIユースケース台帳
- 台帳の項目 14〜20個（例：ID、名称、業務と目的、所管部門・責任者（Owner）、利用者、使うモデル・サービスと提供者、入力データの区分（個人情報・機密）、出力の使われ方（人の判断の補助か自動か）、リスク階層と判定日、適用規制・法域、評価結果と合格基準、監視指標、契約・SoA の参照、稼働状態、次回見直し日、廃止日）。各項目に「なぜ要るか」と記入例。
- 登録から廃止までの流れ 6〜8段階（登録の契機、一次判定、審査、承認、本番、定期見直し、変更時の再評価、廃止）。
- シャドーAIの見つけ方 4〜6個（SaaS のログ・CASB・経費・調達・アンケート・ブラウザ拡張 など。判断として書く）。
- 出典の例：ISO/IEC 42001（取れなければ使わない）、NIST AI RMF の GOVERN/MAP（AI system inventory に触れている箇所）、AI事業者ガイドライン、米OMB の AI ユースケース・インベントリ。

## 3. eval：AIの検証（性能・安全性）の手法
- 検証の種類 8〜12個：オフライン評価（評価用データセット）、タスク別の指標（分類の適合率・再現率、RAG の根拠への忠実さ・回答の関連性 など）、AIによる自動採点（LLM-as-a-judge）とその校正、人手評価、レッドチーミング、安全性評価（有害出力・情報漏えい・プロンプトインジェクション耐性）、公平性・偏りの検査、頑健性、負荷・コスト、A/B・カナリア、本番の継続評価とドリフト監視、第2線の独立検証（モデルリスク管理）。
  各項目：何を確かめるか／いつ（導入前・変更時・本番中）／誰が／代表的な指標や方法／落とし穴。
- 合格基準の決め方 4〜6項目（リスク階層に比例、ベースラインとの比較、失敗の重さで閾値、再評価の条件）。
- 出典の例：日本AISI「AIセーフティに関する評価観点ガイド」「レッドチーミング手法ガイド」、NIST AI 600-1（生成AIプロファイル）・AI RMF の MEASURE、金融庁「モデル・リスク管理に関する原則」。

## 4. riskai：リスク管理領域でのAI活用
- 活用の場面 8〜12個：与信・引受の審査補助、AML の取引モニタリングと誤検知の削減、不正検知、契約・委託先審査の一次チェック、規程・法令改正の影響分析、KRI/KPI の常時モニタリングと異常の早期警戒、内部監査（全件テスト・継続的監査）、統制テストの自動化、インシデント・苦情の分類 など。
  各場面：AIがすること／人が残すこと（最終判断）／主なリスク（説明できない判断・誤検知の偏り・自己監査の独立性）／必要な統制。
- KRI/KPI のモニタリングの型 4〜6個（例：指標の定義と閾値、データの鮮度、アラートの責任者、AIが出す早期警戒の扱い）。
- 出典の例：金融庁 AIディスカッション・ペーパー（金融機関のAI活用事例・リスク）、マネロン対策ガイドライン、モデル・リスク管理の原則、内部監査の基準（IIA は取れれば）。

{"cust": {"pre": [{"c": ["項目", "item"], "why": ["理由", "..."], "src": [ ...任意 ]}], "run": [...], "inc": [...]},
 "inv": {"fields": [{"f": ["項目名", "..."], "why": ["..."], "ex": ["記入例", "..."]}], "flow": [{"s": ["段階", "..."], "d": ["内容", "..."]}], "shadow": [{"c": [...], "d": [...]}], "src": [...]},
 "eval": {"kinds": [{"k": [..], "what": [..], "when": [..], "who": [..], "how": [..], "trap": [..], "src": [...任意]}], "accept": [{"c": [..], "d": [..]}]},
 "riskai": {"uses": [{"a": [..], "ai": [..], "human": [..], "risk": [..], "ctl": [..], "src": [...任意]}], "kri": [{"c": [..], "d": [..]}]},

- 日本語は1項目60字以内を目安、英訳を付ける。
- `src` を付けた項目は quote で裏づける。付けない項目は判断・ベストプラクティスとして書く（特定の規格の要求のように書かない）。

ページの取り方・検査は REG_BRIEF.md と同じ（`sh tools/fetch.sh k_kit <名前> <URL>`、`python3 -I tools/qcheck.py k_kit/kit.json` で PROBLEMS: 0）。
