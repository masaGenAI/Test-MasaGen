# Project Nova 整合性点検

Project Nova は 60MB を超える単一ファイル（`nova-app/src/ProjectNova.jsx`）に9つのハブを抱えている。
同じ事実（問題数、出典の種類、企業数、人物の肩書など）が、ポータルのタグ・Mastery Track・タブの説明文・
コメント・画面に出ない計画データに**別々に書き写されている**ため、どこか1か所を更新すると他が古いまま残る。
実際にこの点検で見つかったもの：

- Book-Summary に note を足したのに、ポータルのタグは「flier・Kindle・YouTube」のまま
- 企業研究は23社なのに、Mastery Track は「企業研究22社」
- 問題を12問足したのに、Mastery Track の問題数と難易度内訳が古いまま（重複削除の前の値まで残っていた）
- YouTube の動画・note の記事まで「冊」で数えていた
- 社長が交代しているのに、日本法人の情報が前任者のまま（しかも読みが誤っていた）

このスキルの目的は2つ。**いま食い違っている箇所を全部直すこと**と、**直すときに数字をデータから数える形に変えて、次に同じずれが起きないようにすること**。

## 手順

### 1. 何が変わったかを把握する

点検の範囲を決めるため、前回の点検以降の変更を確かめる。

```bash
git log --oneline -30 -- nova-app/
```

問題の追加・削除、出典・タブ・企業の追加、実在の人物・組織の情報更新があれば、それぞれ下の「変更の波及先」を必ず見る。
ユーザーがスクリーンショットで具体的な箇所を示している場合は、そこを起点にして同じ種類の記載を横断で探す。

### 2. 実数を数える

```bash
python3 .claude/skills/nova-consistency-audit/scripts/facts.py
```

技術道場（MCQS）のテーマ別問題数・用語辞典、各道場のバンク（領域別）、DEV_QUIZ、理解度チェック、
TechHub のタブ数・企業数、言語学のカテゴリ・分野数、資格数、Book-Summary の出典別件数を、ソースから直接数える。
これが以降の「正解」になる。数えるときは必ずこのスクリプトを使う。正規表現で雑に数えると、
文字列内の括弧やクォート、入れ子の配列（DEV_QUIZ はカテゴリの中に questions を持つ）、
concat で組み立てるバンク（CHECK_*）で数え間違える。実際に過去に外れている。

### 3. 古い記載を検出する

```bash
python3 .claude/skills/nova-consistency-audit/scripts/stale_scan.py            # MISMATCH と OK
python3 .claude/skills/nova-consistency-audit/scripts/stale_scan.py --review   # 数字＋単位の記載を全部
```

- **MISMATCH**：既知の種類の記載（企業数、Book-Summary の件数、出典の列挙の漏れ、用語辞典の問題数、
  言語学の分野数、資格数、道場の問題数など）が実数と違う。直す対象。
- **REVIEW**：数字＋単位の記載のうち、自動では実数と結びつけられないもの。数百件あるので全部は読まない。
  手順1で分かった「変わったもの」に関係する語（例：Slalom、note、企業研究、クイズ）で絞って目を通す。
  問題文の中の数字（業界ニュースの「16社」など）はコンテンツなので直さない。

スキャンは網羅ではない。文言の食い違い（出典名・人物名・肩書・タブ名）は数字を含まないことが多いので、
次の「変更の波及先」で該当するものを grep で確認する。

### 4. 変更の波及先を確認する

| 変わったもの | 確認する場所 |
|---|---|
| 技術道場（MCQS）の問題の追加・削除 | 技術道場のタイトル・テーマの問題数（自動）、Mastery Track の各テーマ行と難易度内訳（`mqRow` で自動）、ポータルの TechHub タグ（自動）、復習スケジュール `gafa_srs_v1`（添字で保存。削除・並べ替えをするなら添字の付け替えが要る）。問題を作る・直すときは quiz-authoring スキルに従う |
| 道場系バンク（実務論点マップ・Slalom・ガバナンス道場・理解度チェック）の追加・削除 | Mastery Track の行（`mqDoms` で自動）、弱点レーダーの `WEAK_SOURCES` の領域名、`CheckEngine` の復習キュー（添字で保存。削除したら `removedIdx` を渡して詰め直す）、領域あたりの問題数と出題範囲の区切り（`partSize`） |
| TechHub にタブを追加 | `TABS`＋ラベル辞書 `tab_xxx`＋描画分岐＋ナビのグループ、Mastery Track の実務行（`BOOTCAMP_QUEST.practice`）とクイズ行（`mega`）、弱点レーダー、ポータルのタブ数（自動） |
| Book-Summary の出典・件数 | `booksummaryhub.html` の `SOURCES` と取り込みデータ、件数の単位（`unitFor`：本は冊、動画・記事は件）、ハブの説明文、ポータルのタグと自由選択トラックの説明（`BOOK_SUMMARY_HTML` から自動で数える）、関連タブとの相互参照（例：TechHub の実務論点マップ） |
| 企業研究の企業 | `COMPANIES`、比較表、「主要N社」「N社の組織」の見出し、Mastery Track の「企業研究N社」（自動） |
| 実在の人物・組織の事実（社長交代など） | その名前・肩書を全ファイルで grep し、企業研究カード・道場の基本情報・グローバル事例・クイズの問題と解説を**同時に**直す。事実は evidence-research の考え方で裏付け、確認の程度（本文を取得できたか、検索結果の一致だけか）と時点を明記する。推測で埋めない |
| 言語学・資格・Finance などの構成 | ポータルのタグ（言語学は自動、Finance・Consulting・Language は固定の文言）と、Mastery Track の自由選択トラックの説明 |

### 5. 直す

原則は**数字を手で書き直すのではなく、データから数える形に置き換える**こと。書き直しただけでは次の追加でまたずれる。
ただし既に自動化されている箇所（ポータルのタグ、Mastery Track の問題数、技術道場の件数）は、データ側を直せば追従する。

直すときにはまりやすい点（どれもこのリポジトリで実際に起きた）：

- **モジュールの内側は外から見えない。** 各ハブは `const XxxHubModule = (function () { ... return Component; })();` の中に
  閉じている。MCQS などのバンクはトップレベルからは参照できず、参照すると「MCQS is not defined」で**ポータルごと白画面になる**。
  返すコンポーネントの静的プロパティとして渡し（例：`GafaHub.MASTERY_BANKS`、`GafaHub.TAB_COUNT`、
  `LinguisticsHub.FIELD_STATS`）、外側では `MegaTechHubModule.MASTERY_BANKS` のように読む。
- **宣言順（TDZ）。** トップレベルの `const` は上から順に評価される。ポータルの `NOVA_STATIONS` は `BOOTCAMP_QUEST` より前にあるので、
  タグは getter（`get tagJa() {...}`）と遅延計算（`novaStats()`）で描画時に数える。
- **ユーザーの記録を壊さない。** 復習スケジュール・復習キュー・完了チェックは、問題の添字や範囲のキーで端末に保存されている。
  問題の削除・並べ替え・区切り方の変更をするときは、付け替えの処理を入れるか、キーを分けて誤った問題に記録が付かないようにする。
  付け替えられず空に戻る記録があるなら、報告でそう伝える。
- **画面に出ないデータとコメントも直す。** 使われていない計画データやファイル先頭のコメントに古い数字が残ると、
  次の作業者がそれを正しいと思って書き写す。数字を持たない説明に変えるのが安全。
- **単位と表記をそろえる。** 本は「冊」、動画・記事は「件」。問題の範囲は「パート」ではなく「1〜100問目」のように問題番号で示す
  （ユーザーが「パート」は分かりにくいと指摘済み）。範囲はテーマの境目で区切り、テーマをまたがせない。
- **タグや見出しを長くしたら狭い画面で確認する。** ポータルの目次タグは幅 390px で題名に重なった。

### 6. 検証する

```bash
cd nova-app && npm run build        # 問題バンクの検査（validate-quiz）→ vite のビルド
cd .. && node .claude/skills/nova-consistency-audit/scripts/smoke.mjs [スクリーンショットの保存先]
python3 .claude/skills/nova-consistency-audit/scripts/stale_scan.py   # MISMATCH 0 を確認
```

`smoke.mjs` はポータルの目次タグと Mastery Track の数字を表示し、9つのハブを開き、TechHub の全タブを順に押し、
Book-Summary の出典別件数と単位を表示して、実行時エラーを数える。全体で数分かかるので、バックグラウンドで実行してよい。
表示された数字が `facts.py` と一致すること、実行時エラーが0件であることを確かめる。
タグや見出しを変えたときは、幅 390px のスクリーンショットでも重なりがないかを見る。

### 7. コミットして報告する

コミットはリポジトリの規約に従う（命令形・1行目50文字以内、指定の末尾行）。指定のブランチにプッシュする。PR は頼まれない限り作らない。

報告は日本語で、次の形にする。ユーザーはコードではなく画面で確かめるので、画面上の場所と表示の変化で書く。

```markdown
Project Nova全体を点検し、〇〇と食い違っていた箇所を直しました。（プッシュ・反映の状況を1文で）

## 直した箇所
| 場所 | 直す前 | 直した後 |
|---|---|---|
| （画面上の場所） | （古い表示） | （新しい表示。自動で数える形にしたならそう書く） |

## 確認済みで、変更不要だった箇所
- （点検して一致していたもの。ユーザーが心配しそうな箇所を中心に）

## 動作確認
- （開いたハブ・タブの数、実行時エラーの件数、ビルドの結果）

## 記録について（該当するときだけ）
- （完了チェックや復習履歴がどうなるか。空に戻るものがあれば必ず書く）
```

## スクリプト

- `scripts/facts.py` — 実数表（`--json` で JSON）。数秒。
- `scripts/stale_scan.py` — 古い記載の検出。`--review` で全件、`--jsx <path>` で別の版のファイルを検査できる
  （`git show <rev>:nova-app/src/ProjectNova.jsx > /tmp/old.jsx` と組み合わせると、検査が古い記載を拾えるかを確かめられる）。
- `scripts/smoke.mjs` — ブラウザでの確認。先に `npm run build` で `nova-app/dist` を作っておく。
  playwright-core は `nova-app/node_modules` から、Chromium は `/opt/pw-browsers/chromium` から読む（`playwright install` はしない）。

スキャンの規則（`stale_scan.py` の `RULES`）は、新しい種類の記載が食い違ったのを見つけたら追加していく。
規則を足したら、その記載が古かった頃の版に対して実行し、実際に MISMATCH になることを確かめる。
