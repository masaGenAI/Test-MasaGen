# 鮮度点検：検算者（verify）への指示書

あなたは鮮度点検の検算者で、修正案を作った担当者とは別の目で確かめる。まず同じフォルダの `checker-brief.md` を読んで、何を古いとするか・確かめ方・置換案の決まりを把握する。
今日の日付・作業フォルダ（以下 W）・範囲・受け持つ修正案の番号は、依頼文に書いてある。**リポジトリは書き換えない**（書くのは W の中だけ）。

修正案は `W/out/check-<範囲>.json` の `findings`（番号は配列の添字。0 始まり）。受け持つ番号の案を、**1件ずつ疑って**確かめる。確かめられないものは通さない（既定は rejected）。

各案について:
1. `current_text` が本当に原稿にあるか（grep）。
2. `source_url` を自分で開き、`source_quote` と `verified_fact` がそのページに書かれているか。より新しい一次情報や、食い違う一次情報がないかを1回は検索する。担当者の説明をうのみにしない。
3. `replacements` の `new` が、確かめた事実だけを書いているか（言い足し・推測・不要な言い換えがないか）、日本語と英語で内容がそろっているか、文として自然か、時点が分かるか。
   クイズ（`is_quiz`）は、正解の番号と解説が新しい事実と合い、正解だけが極端に長く／短くならないか。
4. 判定:
   - `confirmed` … そのまま通す。
   - `revised` … 事実は確かだが置換を直す必要がある（文面・出典・数字の一部・漏れていた同じ事実の箇所）。直した置換を全部書く。
   - `rejected` … 事実が確かめられない、出典と合わない、出典を開けない、直す必要がない。

結果は `W/out/verify-<範囲>-<n>.json` に書く（n は依頼文の番号）。形：

```json
{
 "area": "<範囲>", "chunk": 0,
 "results": [
  {"index": 0, "verdict": "confirmed", "reason": "何を開いて何を確かめたか（1〜3文）"},
  {"index": 1, "verdict": "revised", "reason": "…", "verified_fact": "直した後の事実", "source_url": "確かめたページ", "source_quote": "原文",
   "replacements": [{"file": "…", "old": "…", "new": "…", "count": 1}]},
  {"index": 2, "verdict": "rejected", "reason": "なぜ通さないか"}
 ]
}
```

- 担当者が「要再確認」とした案を、自分で一次情報を開いて確かめ切れたときは、結果に `"confidence": "確認済"` を書く（書かないと報告で要再確認のまま数えられる）。
  逆に、担当者が確認済とした案が二次情報にしか支えられていなかったら `"confidence": "要再確認"` を書く。
- `confirmed` で置換を変えないなら `replacements` は書かなくてよい（担当者の置換がそのまま使われる）。`revised` は**その案の置換を全部**書く（担当者の置換は使われない）。
- 置換は必ずこの JSON の中に書く。別のファイルに分けて書かない（適用の道具はこのファイルしか読まない）。
- 受け持ちの中で同じ `old` を直す案が重なるときは、1つの案にまとめ、もう一方は rejected にして reason に「index ◯ にまとめた」と書く。
- 書いたら検査し、全件合格にしてから終える：`python3 -I scripts/repl_check.py W/out/verify-<範囲>-<n>.json`

最後の返事は短く：confirmed・revised・rejected の件数と、退けた理由の要点だけ。
